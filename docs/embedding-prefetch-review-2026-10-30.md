# 2026-10-30 선행 임베딩 로컬 검토본

**최종 상태: 실제 비교 후 선행 임베딩은 기본 비활성화했습니다. 답변별 소요시간 표시는 유지합니다.** 기존 검색·판단 경로로 실행 중이며, 아래 최초 적용 기록과 구분합니다.

사용자 승인 후 응답시간 표시와 기본 OFF인 실험 코드를 v0.3.3으로 정식 릴리스했습니다. 아래 기록은 배포 전 로컬 검토 과정입니다. 기존 v0.3.2 검색·판단 로직은 유지합니다.

## 복구 지점

- Git 기준: `pb-before-embedding-prefetch-20261030` (v0.3.2와 같은 커밋)
- 이전 실행 이미지: `project-brain-mvp-app:before-embedding-prefetch-20261030`
- DB 스키마·기존 문서는 변경하지 않습니다. 수동 성능 확인 질문은 일반 질문처럼 대화/추적 기록을 남깁니다.

## 변경 범위

- LLM 계획이 필요한 독립 답변 질문에서 원 질문 임베딩과 계획을 병렬 실행합니다.
- 빠른 결정형 경로·참조형 후속 질문·작성 요청은 기존 경로를 유지합니다.
- 확정 검색어와 문자열이 정확히 일치하고 작업이 이미 완료됐을 때만 사용합니다. 불일치·실패·지연 시 기다리지 않고 기존 임베딩 경로로 진행합니다.
- 투기적 API 호출은 3초 timeout/재시도 없음, 최대 2개 동시 작업, 대기 큐 없음입니다. 늦어진 실행 중 호출은 취소되지 않을 수 있고 추가 호출 비용이 생길 수 있습니다.
- 사용되지 않은 벡터는 캐시에 넣지 않습니다. 사용된 벡터는 기존 캐시 정책에 따릅니다. 검색 점수·후보 상한·계층·근거 판단·답변 생성은 변경하지 않습니다.
- SearchTrace에 기능 활성화 여부와 준비된 검색어 수만 기록하고 벡터는 기록하지 않습니다.
- UI는 제출 시점부터 답변 렌더링 및 페인트 기회까지 브라우저 경과시간을 표시합니다. 진행/완료/실패 시간을 각 답변에 남깁니다. 백그라운드 탭에서는 브라우저 렌더링 스케줄 영향이 있습니다.
- 이전 정적 파일 캐시와 혼동되지 않도록 검토본 전용 캐시 키를 사용합니다.

## 실행

기존 의존성을 보존한 검토 이미지로 앱만 교체합니다. 기본값은 선행 처리 OFF이며 시간 표시 UI는 포함됩니다.

```bash
cd /path/to/project-brain-mvp
docker compose -f docker-compose.yml -f docker-compose.prefetch-review.yml up -d --build --no-deps app
```

실험 재개를 명시적으로 선택할 때만 선행 처리 켜기:

```bash
SEARCH_EMBEDDING_PREFETCH=true docker compose -f docker-compose.yml -f docker-compose.prefetch-review.yml up -d --no-build --no-deps app
```

이전 실행 이미지로 완전히 복귀 (새 시간 표시 UI도 이전으로 돌아갑니다):

```bash
docker compose -f docker-compose.yml -f docker-compose.prefetch-rollback.yml up -d --no-build --no-deps app
```

DB 볼륨 삭제나 `git reset --hard`는 필요하지 않습니다. 릴리스 작업 브랜치는 `codex/v0.3.3-response-timing`입니다.

## 검토 기록

- 오프라인 기존/추가 회귀 테스트: 84개 통과.
- UI 진행/완료/실패 표시 및 완료 후 타이머 정지: 브라우저 모의 응답으로 점검.
- 화면 표시 시간 원자료: `data/performance-review/20261030/before.json`, `after.json` (Git 제외).
- 각 질문 한 번의 실행 관찰로 p50/p95나 전체 정확도 개선을 주장하지 않습니다. 외부 API 지연·생성 분량·계획 결과·캐시 상태가 달라질 수 있습니다.

### 실제 실행 상태와 측정 제한

- 검토 이미지를 localhost:8000에 적용하고 `search_embedding_prefetch=True`를 확인했습니다. 정식 버전 문자열은 여전히 0.3.2이며 정식 릴리스를 의미하지 않습니다.
- 변경 전 브라우저 측정: 김그륜 상세 질문 26,762ms / 6월 영상 목록 2,632ms (각 1회).
- 중간 실제 요청은 외부 API 한도 오류로 실패해 성능 표본에서 제외했습니다. 이후 재개해 아래 비교를 완료했습니다.
- 84개 오프라인 회귀 테스트 및 UI 모의 응답 테스트를 통과했습니다.

### 충전 후 실제 비교 완료

아래는 질문 제출 직전부터 완성 답변을 렌더링하고 브라우저 페인트 기회를 거친 시점까지의 측정입니다. 각 조건 1회이며 통계적 벤치마크가 아닙니다. 원자료는 `before.json`, `after.json`, `disabled.json`입니다.

| 질문 | 기존 이미지 | 선행 ON | 선행 OFF + 시간 표시 |
| --- | ---: | ---: | ---: |
| 김그륜 바이브코딩 상세 | 26.762초 | 26.504초 | 20.624초 |
| 6월 영상 제목·업로드 시간 | 2.632초 | 2.058초 | 1.910초 |

- 첫 일반 질문의 확정 검색어가 원 질문과 정확히 일치하지 않아 `prepared_query_count=0`이었습니다. 따라서 ON 측정의 감소를 선행 임베딩 효과로 평가할 수 없습니다. 빠른 목록 경로는 원래 선행 처리가 제외됩니다.
- 일반 질문은 동일한 원문 문서 1개를 인용하고 supported 판정을 유지했습니다. 생성 문장과 분량은 달라졌으므로 정확도 개선으로 주장하지 않습니다.
- 영상 목록은 16개 근거의 순서와 표시 답변이 모두 일치했습니다.
- 일반 질문 ON의 단계별 시간은 계획 2.212초, 후보 검색 5.407초, 근거 구성 0.085초, 판단·답변 생성 18.630초입니다. 이 실행에서는 판단·생성 구간이 대부분을 차지했습니다. 전체 질문으로 일반화하지 않습니다.
- 별도 OFF 비교는 컨테이너 재생성 후 진행했습니다. 프로세스 캐시는 초기화되지만 DB/외부 API 상태와 LLM 계획·생성은 고정되지 않았습니다. OFF가 구조적으로 더 빠르다는 결론도 내리지 않습니다.
- UI 실제 표시 `응답 완료 · 20.5초`, `응답 완료 · 1.8초`를 확인했습니다. 자동화 도구의 외부 측정에는 클릭 전달·화면 관찰 지연이 조금 더 포함됩니다.
- 효과가 입증되지 않은 추가 호출을 계속 발생시키지 않도록 `SEARCH_EMBEDDING_PREFETCH=false`로 유지하고 compose 검토 설정 기본값도 false로 변경했습니다. 시간 표시 UI는 활성 상태입니다.
- 이 검토 후 사용자 승인으로 v0.3.3 정식 릴리스를 진행합니다. 완전 복구는 보존 이미지와 위 rollback 명령을 사용합니다.

### 측정 도구

`scripts/measure_prefetch_preview.mjs`는 로컬 설치된 Playwright 모듈 경로(`PB_PLAYWRIGHT_MODULE`), 프로젝트 UUID(`PB_REVIEW_PROJECT_ID`), 질문 배열 JSON 파일 경로(`PB_REVIEW_QUESTIONS_FILE`)를 실행 환경으로 전달받습니다. 질문 파일과 측정 출력은 Git에서 제외되는 `data/performance-review/` 아래에 보관합니다. 실제 API를 호출하고 일반 대화·추적 기록을 남기므로 승인된 소수 질문으로 실행합니다.
