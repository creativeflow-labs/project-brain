# Project Brain 제품 로드맵

이 문서는 장기 프로젝트에서 기능 누락을 방지하기 위한 제품 로드맵이다. 확정된 설계 원칙은 [DECISIONS.md](DECISIONS.md), 출시별 변경 사항은 [CHANGELOG.md](../CHANGELOG.md)에서 관리한다.

## 제품 정의

Project Brain은 흩어진 프로젝트 기록을 연결해 무엇이 왜 결정됐고, 현재 누가 무엇을 해야 하는지 원문 근거와 함께 답하는 팀용 AI 브레인이다.

핵심 경험:

> 딱 우리 팀 정보이고, 우리 팀 프로세스다.

## 현재 1차 목표

Project Brain을 로컬 환경에서 작은 조직이 실제 업무에 사용할 수 있는 수준의 비공개 MVP로 완성한다.

진행 순서:

1. 검색·판정 코어 고도화
2. 웹·모바일 UI 고도화
3. 추가 데이터 소스의 단계적 연결과 회귀 테스트
4. 외부 조직 데이터 기반 모의 운영
5. 인증·격리·토큰·로그·백업 보안 점검
6. 핵심 기능 품질 기준 점수 통과
7. 팀장용 검증 브리핑·알림함 고도화와 로컬 운영 검증
8. 알림을 포함한 로컬 MVP 최종 승인

알림은 중요한 고도화 항목이지만 현재 1순위는 아니다. 검색·판정, UI, 데이터 연결, 외부 조직 수준의 품질·보안 검증을 먼저 완료한다. 팀장용 검증 브리핑·알림함은 이 핵심 기능을 기반으로 구현하고 로컬에서 검증한 뒤 Railway로 마이그레이션한다. 네이버웍스 등 외부 알림 채널은 Railway 안정화 이후 연결한다.

## 단계별 로드맵

### 1단계: 검색·판정 코어

- [x] 기준 질문·정답·필수 근거·금지 답변으로 구성된 1차 회귀 테스트 세트
- [x] 대화 스레드와 후속 질문의 활성 회사·사건·필드 유지
- [x] 독립형 검색 질문 재작성
- [x] 의미·키워드·정확 일치·메타데이터 다중 후보 검색
- [x] 출처별 후보 확보, 결과 통합, 재순위화
- [x] 근거 부족과 충돌 가능성 평가 후 제한 재검색
- [x] Notion 부모·인접 블록 문맥 복원
- [x] Gmail 원문·회신 스레드 복원과 기본 인용문 중복 제거
- [x] 질문 시점의 사건·출처·발신자 역할·시점·상태 비교
- [x] 지원됨·충돌·근거 부족 내부 판정
- [x] 답변 인용 번호와 직접 근거 순서 일치 검증
- [x] 검색계획·후보문서·판정근거 실행 추적

현재 상태:

- `v0.4.0-alpha.3`에서 상태 검증과 함께 명료한 판정 보고, 담당자·금액 역할 분리, 출력 안전 검증, 근거 중복·순서 정리를 구현했다.
- 질문 시점의 상태 판정은 구조화해 저장하지만, 모든 수집 문서의 사건·주장을 사전에 영구 구조화하는 단계는 아직 남아 있다.
- 더 다양한 실제 질문 세트로 상태 정확도·결정적 근거 재현율·충돌 오탐을 점수화한 뒤 정식 버전을 승인한다.

완료 기준:

- 후속 질문이 이전 사건을 안정적으로 이어간다.
- 충돌 질문에서 양쪽 근거가 모두 최종 판정에 포함된다.
- 정보가 없을 때 임의의 숫자나 담당자를 확정하지 않는다.
- 작은 청크가 부모 문서와 사건 문맥 안에서 해석된다.
- 잘못된 확정 답변 0건을 포함한 기준 점수를 통과한다.

### 2단계: 웹·모바일 UI

- [x] 확인됨·충돌·확인되지 않음 상태 표시
- [x] 현재 상태·기준 시점·다음 확인·미니 시간축 표시
- [x] 한 줄 결론·판정·역할별 사실·다음 확인 구조화 답변
- [x] 답변 사실별 직접 근거 연결
- [x] Markdown 기호가 노출되지 않는 구조화 DOM 렌더링
- [x] 세부 내용·판단 근거·피비의 제안 기본 노출과 답변 가독성 개선
- [x] 대화·근거 패널 높이 및 내부 스크롤 안정화
- [x] 핵심 판단 근거 중복 제거와 우측 패널의 관련 보조 원문 유지
- [ ] 모바일 근거 패널과 원문 열기 개선
- [ ] 대화 스레드 생성·전환·초기화
- [ ] 검색·판정 진행 상태와 오류 안내
- [ ] 연결 상태, 마지막 동기화, 실패 항목, 재시도 상태 통합 표시

완료 기준:

- 모바일에서 질문부터 근거 원문 확인까지 핵심 흐름을 완료할 수 있다.
- 사용자가 AI의 결론과 원문 사실을 명확하게 구분할 수 있다.
- 충돌과 정보 부재 상태가 일반 답변처럼 표시되지 않는다.

### 3단계: 지식 데이터 연결 확대

- [x] 일반 업로드 PDF·DOCX·TXT·MD
- [x] Notion 접근 범위 발견과 증분 동기화
- [x] Gmail OAuth 연결과 본문 동기화 실사용 검증
- [ ] Gmail 스레드·인용문 중복 제거와 첨부파일 실사용 검증
- [ ] Google Drive 연결
- [ ] 출처별 외부 원본 식별자와 중복 자료 관리

완료 기준:

- 각 출처가 서로 덮어쓰거나 섞이지 않는다.
- 변경·삭제·권한 회수가 예측 가능하게 반영된다.
- 모든 검색 근거에서 원본을 열 수 있다.

### 4단계: 출처 제어형 다중 검색

- [ ] 검색 범위 UI: 전체·Notion·Gmail·Drive·업로드
- [ ] 복수 출처 선택
- [ ] 검색 범위를 후속 질문에 유지
- [ ] 같은 질문을 단일 출처와 전체에서 비교하는 회귀 테스트
- [ ] 최신 정보와 과거 정보 충돌 감지
- [ ] 공식 문서, 대화, 초안의 성격 구분
- [ ] 중복 문서와 이메일 답장 인용 제거
- [ ] 전체 검색의 출처별 결과 수 균형 조정
- [ ] 답변 전 근거 충분성 검증

완료 기준:

- 사용자가 지정한 출처 밖의 자료가 답변 근거에 포함되지 않는다.
- 전체 검색에서 충돌을 숨기지 않고 출처와 시점을 설명한다.
- 검색 결과가 늘어나도 핵심 프로젝트 식별자와 최신 결정의 정확도가 유지된다.

### 5단계: 프로젝트 시간축

- [ ] Google Calendar 읽기 전용 연결
- [ ] 필요 시 팀이 사용하는 다른 Calendar 연결 검토
- [ ] 일정·회의·마감과 프로젝트 문서·메일 연결
- [ ] 일정 변경 이력과 발생 시점 보존
- [ ] 회의 전 관련 문서·메일·미완료 업무 요약

대표 질문:

- 이번 주 마감은 무엇인가?
- 내일 회의 전에 확인해야 할 내용은 무엇인가?
- 일정 변경의 이유와 관련 대화는 어디에 있는가?

### 6단계: 팀 워크플로우

- [ ] 첫 고객군이 실제 사용하는 업무관리 서비스 선정
- [ ] 업무·담당자·상태·우선순위·의존 관계 읽기
- [ ] 프로젝트·업무·일정·결정·승인 공통 모델 구축
- [ ] 이메일과 문서의 결정이 실제 업무 상태에 반영됐는지 검증
- [ ] 지연 요인, 승인 대기, 담당자 공백 감지

대표 질문:

- 지금 이 프로젝트를 막고 있는 것은 무엇인가?
- 다음 행동은 무엇이고 담당자는 누구인가?
- 문서에서 확정된 결정이 업무관리 서비스에 반영됐는가?

### 7단계: 팀장용 검증 브리핑·알림함

우선순위 원칙:

- 알림은 검색·판정 코어와 시간·업무 흐름 이해를 대체하지 않는다.
- 핵심 기능의 정확도와 데이터 연결 안정성을 먼저 통과한 뒤 구현한다.
- Railway 마이그레이션 전에 로컬 환경에서 생성·중복 방지·근거 추적·재시작 복구를 검증한다.

1차 범위:

- [ ] 마지막 확인 이후 Notion·Gmail 변경분 자동 동기화
- [ ] 새로운 기록에서 충돌·결정 변경·승인 근거 부족·미반영 변경 후보 탐지
- [ ] 팀장이 피비를 열 때 `오늘의 검증 브리핑` 생성
- [ ] 프로젝트별 알림 유형·중요도·근거·발견 시점·상태 저장
- [ ] 같은 사건과 근거에서 생성된 알림의 중복 방지
- [ ] 확인·잘못된 알림·해결됨 피드백과 판정 이력 보존
- [ ] Docker 중단·Mac 잠자기 이후 재실행 시 누락 기간 따라잡기
- [ ] 웹·모바일 알림함과 근거 원문 열기

초기 알림 유형:

- 출처 간 사실 충돌
- 최근 변경된 결정과 상태
- 승인·확정 근거 부족
- 이메일 등에서 바뀐 내용이 공식 문서나 업무 상태에 반영되지 않음

완료 기준:

- 근거가 없는 알림을 생성하지 않는다.
- 동일 알림을 반복 노출하지 않는다.
- 모든 알림에서 판정 이유와 원문으로 역추적할 수 있다.
- 로컬 실행이 중단돼도 재시작 후 변경분을 복구한다.
- 알림 생성이 검색 API의 응답성과 데이터 동기화 안정성을 훼손하지 않는다.

범위 제외:

- 네이버웍스·이메일·모바일 OS 외부 푸시는 Railway 안정화 이후 전달 채널로 추가한다.
- 실시간 이벤트 알림은 Notion Webhook, Gmail Push 등 공급자별 이벤트 연결을 검증한 뒤 도입한다.

### 8단계: 승인 기반 실행

- [ ] 일정 생성·변경
- [ ] 업무 생성·담당자 지정·상태 변경
- [ ] 메신저 알림과 승인 요청
- [ ] 실행 전 변경 대상·내용·영향 범위 미리보기
- [ ] 명시적 승인, 감사 로그, 실패 복구

원칙:

- 읽기 기능을 먼저 안정화한다.
- 쓰기 기능은 기본적으로 승인 없이는 실행하지 않는다.
- 검색 오류가 실제 업무 변경으로 이어지지 않도록 검색·판단·실행 계층을 분리한다.
