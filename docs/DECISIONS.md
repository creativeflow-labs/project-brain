# Project Brain 주요 결정 기록

## ADR-001: Notion 인증 단계화

- 기록일: 2026-07-25
- 상태: ADR-002로 대체
- 담당: Project Brain 개발

### 현재 결정

사내 MVP와 기능 검증 단계에서는 Notion `액세스 토큰` 방식을 사용한다.

- 대상: 단일 사내 Notion 워크스페이스
- 목적: Notion 수집 → RAG 검색 → 네이버웍스 질의응답 흐름의 정확도와 안정성 검증
- 현재 구현: 사용자가 Project Brain 화면에 액세스 토큰과 페이지 URL을 입력해 문서를 가져온다.
- 제한: 토큰을 영구 저장하지 않으며, 자동 동기화와 고객용 연결 UX는 아직 제공하지 않는다.

### OAuth 전환 조건

다음 중 하나를 시작하기 전에 Notion OAuth 2.0 연결을 구현한다.

- 외부 고객 대상 파일럿
- 여러 고객사 또는 여러 Notion 워크스페이스 지원
- 사용자가 토큰을 직접 복사하지 않는 정식 연결 경험
- 주기적 자동 동기화

### OAuth 고도화 필수 항목

- Notion 공개 연결과 OAuth 콜백 구현
- CSRF 방지를 위한 `state` 검증
- 워크스페이스별 액세스 토큰·리프레시 토큰 암호화 저장
- 토큰 갱신, 만료, 폐기 및 재연결 처리
- 연결할 페이지 선택과 최소 권한 적용
- 고객사별 데이터·토큰 격리
- 연결 상태, 마지막 동기화 시각, 오류 이력 표시
- 자동 동기화 스케줄러와 재시도 정책
- 연결 해제 시 토큰 및 동기화 데이터 처리 정책
- OAuth 성공·실패·갱신·해제 통합 테스트

### 유지 원칙

액세스 토큰 방식은 사내 개발과 장애 진단용으로 유지하되, 외부 고객이 사용하는 운영 환경의 기본 인증 방식으로 제공하지 않는다.

## ADR-002: Notion 지식공간 자동 동기화

- 기록일: 2026-07-25
- 상태: 확정
- 적용 버전: v0.2.0

### 문제 정의

페이지 URL을 사용자가 매번 입력하거나 Notion 페이지 위계를 Project Brain에 맞춰 재구성하게 하면 변동성이 큰 조직 지식을 안정적으로 운영할 수 없다. 제품이 기존 지식 구조를 흡수해야 하며, 사용자의 Notion 운영 방식을 강제하지 않는다.

### 결정

- 페이지 URL 입력을 기본 사용자 흐름에서 제거한다.
- 사내 단일 계정 검증은 개인 액세스 토큰(PAT)으로 접근 가능한 범위를 자동 탐색한다.
- 내부 연결 토큰도 지원하되, 명시적으로 공유된 범위만 동기화한다.
- 외부 고객 파일럿 전에는 OAuth로 전환한다.
- 토큰은 프로젝트별로 암호화 저장한다.
- 최초 전체 탐색 이후 수정 시각과 콘텐츠 해시를 이용해 증분 동기화한다.
- 자동 동기화와 수동 전체 재검사를 함께 제공한다.

### 완전성 경계

Notion Search API는 접근 가능한 모든 문서의 완전한 열거를 보장하지 않는다. 따라서 PAT 기반 계정 탐색은 `최선 노력`으로 표시하고, 제품에서 `워크스페이스 전체 100% 수집`을 약속하지 않는다. OAuth 제품에서는 사용자가 승인한 범위를 기준으로 동기화 상태와 누락 가능성을 명시한다.

### 안정성 원칙

- 페이지 하나의 실패가 전체 동기화를 중단하지 않도록 격리한다.
- API 속도 제한과 일시 장애에 재시도·지수 백오프를 적용한다.
- 동시 중복 동기화를 프로젝트 단위로 차단한다.
- 검색 누락만으로 기존 문서를 삭제하지 않는다.
- API가 삭제·보관·권한 회수를 확인한 경우에만 인덱스를 제거한다.
- 외부 URL 첨부는 자동 다운로드하지 않고 Notion이 호스팅한 지원 파일만 처리한다.
- 토큰·암호화 키·`.env`는 Git 및 Docker 이미지에 포함하지 않는다.

## ADR-003: 팀 워크플로우를 이해하는 Project Brain으로 확장

- 기록일: 2026-07-25
- 상태: 장기 제품 방향으로 확정
- 적용 시점: 다중 데이터 연결과 검색 품질 검증 이후 단계적 적용

### 제품 목표

Project Brain은 전사 범용 검색이 아니라 팀과 프로젝트 단위의 기억·시간·업무 흐름을 연결하는 운영 두뇌를 지향한다. 사용자가 `우리 팀 정보이고 우리 팀 프로세스다`라고 느낄 수 있도록 문서 검색을 넘어 프로젝트의 현재 상태와 다음 행동을 설명해야 한다.

### 데이터 역할

- Notion·Google Drive·일반 업로드: 공식 지식, 기획, 정책, 산출물
- Gmail·메신저: 논의 과정, 변경 이유, 후속 커뮤니케이션
- Calendar: 일정, 회의, 마감, 시간 변화
- 업무관리 서비스: 담당자, 상태, 우선순위, 의존 관계, 승인
- Project Brain: 여러 출처를 프로젝트 맥락으로 연결하고 근거와 함께 설명

### 검색 범위 원칙

- 수집 시점부터 `project_id`, `source_type`, `connector_id`, 외부 원본 식별자를 분리 저장한다.
- 질문 전에 검색 범위를 제한할 수 있도록 `전체`, `Notion`, `Gmail`, `Drive`, `업로드`, 향후 `일정`, `업무` 범위를 제공한다.
- 복수 출처 선택을 지원하고, 선택된 범위는 후속 질문에서도 유지한다.
- 출처 필터는 검색 후 화면에서 숨기는 방식이 아니라 검색 후보를 만들기 전에 적용한다.
- 전체 검색은 최신성, 공식성, 중복, 출처 균형, 충돌 감지를 계속 고도화한다.
- 장기적으로는 사용자의 질문 의도에 따라 문서·대화·일정·업무 범위를 자동 선택하되, 사용자가 언제든 명시적으로 범위를 통제할 수 있게 한다.

### 워크플로우 확장 순서

1. Notion·Gmail·Google Drive·일반 업로드의 안정적인 읽기 및 동기화
2. 출처별·복수 출처 검색과 전체 검색 비교 테스트
3. Calendar 읽기 전용 연결로 프로젝트 시간축 추가
4. 팀이 실제 사용하는 업무관리 서비스 하나를 읽기 전용으로 연결
5. 프로젝트·업무·담당자·일정·결정·승인·상태 변경·의존 관계를 연결하는 공통 모델 구축
6. 팀장용 검증 브리핑·알림함을 로컬에서 구현하고 변화 탐지·중복 방지·근거 추적 검증
7. Railway 비공개 마이그레이션과 백그라운드 실행 안정화
8. 일정 생성·업무 생성·상태 변경 등 쓰기 기능을 사용자 승인 기반으로 추가
9. 웹과 업무 메신저가 동일한 검색·검증 API를 사용하도록 접점 확장

### 안전 원칙

- 외부 서비스는 읽기 전용으로 먼저 검증한다.
- 일정·업무를 생성하거나 변경하는 기능은 조회 품질과 권한 모델이 안정화된 이후에만 추가한다.
- 쓰기 작업은 대상, 변경 내용, 영향 범위를 사용자에게 보여주고 명시적 승인을 받은 뒤 실행한다.
- 서로 다른 출처의 정보가 충돌하면 임의로 하나를 확정하지 않고 출처·시점·차이를 함께 표시한다.
- 팀별·프로젝트별 데이터와 권한은 전 수집·검색·답변 단계에서 격리한다.

### 현재 범위와의 구분

이 결정은 장기 제품 로드맵이다. 현재 MVP에서는 Notion과 Gmail을 포함한 다중 데이터 연결, 출처 분리, 동기화 안정성, 검색 결과와 원문 근거 검증을 우선한다. Calendar·업무관리·메신저 쓰기 기능은 현재 개발 범위에 포함하지 않는다.

## ADR-004: 검색·판정 코어를 배포와 채널 확장보다 우선

- 기록일: 2026-07-25
- 상태: 확정
- 기준 버전: v0.2.1

### 문제 정의

현재 검색은 질문별로 프로젝트 청크를 평면적으로 순위화해 상위 결과만 답변 모델에 전달한다. 이 구조에서는 후속 질문의 사건 맥락이 사라지고, 상위 검색 범위 밖의 반대 근거가 배제되며, 노션 블록과 이메일 스레드가 사건 단위로 복원되지 않는다.

데이터 연결이 늘어나기 전에 이 문제를 해결하지 않으면 검색 오류와 데이터 동기화 오류가 섞여 원인 추적 비용이 커진다. 같은 상태로 Railway와 업무 메신저를 연결하면 불완전한 답변을 더 많은 접점에 전달하게 된다.

### 결정

- `v0.2.1`을 검색 코어 고도화 전 동작 기준선으로 보존한다.
- Railway 마이그레이션과 네이버웍스 연결은 로컬 MVP 품질 기준 통과 이후로 연기한다.
- 새로운 데이터 소스를 병렬로 늘리기 전에 Notion과 Gmail로 검색·판정 회귀 테스트를 구축한다.
- 다음 검색 코어는 대화 상태, 질문 재작성, 다중 후보 검색, 재순위화, 부모·스레드 문맥 복원, 반대 근거 탐색, 사실 판정을 분리한다.
- LangGraph 또는 동등한 상태형 워크플로를 사용해 검색 계획·검증·재검색·판정 단계를 추적 가능하게 구성한다.
- 프레임워크가 검색 품질을 자동으로 해결한다고 간주하지 않고, 검색 인덱스와 사건·주장 데이터 모델은 별도로 설계한다.

### 개발 순서

1. 검색·판정 합격 기준과 기준 질문 세트 작성
2. 대화 상태와 독립형 질문 재작성
3. 하이브리드 후보 검색과 재순위화
4. 노션 부모 문맥·Gmail 스레드 복원
5. 사건·주장·출처·시점·역할 기반 충돌 판정
6. 답변·인용 근거 검증과 실행 추적
7. 웹·모바일 UI 고도화
8. 추가 데이터 연결
9. 외부 조직 수준의 보안·품질 검증
10. 팀장용 검증 브리핑·알림함의 로컬 운영 검증
11. Railway 비공개 마이그레이션과 안정화
12. 네이버웍스 채널 연결

### 품질 원칙

- 확인된 사실, 상충 정보, 확인되지 않은 정보를 구분한다.
- 이전 AI 답변을 업무 사실의 근거로 사용하지 않는다.
- 작은 청크로 검색하되 청크만 보고 최종 판단하지 않는다.
- 충돌 질문에서는 같은 사건의 반대 근거를 의도적으로 추가 검색한다.
- 모든 핵심 주장은 원문 출처로 역추적할 수 있어야 한다.

## ADR-005: 기존 아키텍처를 유지한 검색 코어 교체

- 기록일: 2026-07-25
- 상태: v0.3.0 알파 구현
- 적용 버전: v0.3.0-alpha.1

### 결정

- 승인된 프로젝트·연결·수집·파싱·문서·청크·FastAPI 구조는 유지한다.
- 기존 `documents`, `chunks`, `connector_credentials` 테이블에는 파괴적 변경을 하지 않는다.
- 대화 상태와 실행 추적은 `conversation_threads`, `conversation_messages`, `search_traces` 새 테이블로 분리한다.
- LangGraph는 데이터 저장소나 연결 계층을 대체하지 않고 질문 계획 → 검색 → 문맥 복원 → 근거 판정 → 제한 재검색의 요청 내부 제어에만 사용한다.
- LangGraph 자체 체크포인터 대신 기존 SQLAlchemy 저장 계층으로 대화를 관리해 운영 경계를 하나로 유지한다.
- 사용자에게 노출하는 `top_k`를 초기 검색 절단선으로 사용하지 않는다. 넓은 후보군에서 검색·통합·재순위화한 뒤 최종 근거만 응답한다.
- 작은 청크는 검색 단위로만 사용하고 최종 판정은 Notion 부모 페이지와 Gmail 스레드 문맥에서 수행한다.
- 근거 상태 분류는 사실을 새로 만드는 장치가 아니라 답변, 재검색, 보류를 결정하는 내부 안전 제어다.

### 비용·안정성 원칙

- 양쪽 원문이 이미 확보된 충돌은 추가 재검색하지 않는다.
- 정보가 부족하거나 충돌 반대편의 독립 출처가 없는 경우에만 최대 1회 재검색한다.
- OpenAI 키가 없을 때도 결정적 로컬 임베딩, 하이브리드 검색, 문맥 복원, 기본 충돌 감지로 회귀 테스트할 수 있어야 한다.
- LLM 호출 실패 시 검색 요청 전체를 실패시키지 않고 결정적 판정으로 폴백한다.
- 검색 실행 추적에는 토큰이나 원문 전문을 복제하지 않고 쿼리·문서 ID·점수·상태만 저장한다.

### 호환성

- 기존 `POST /api/ask` 경로와 `answer`, `mode`, `citations` 응답 필드를 유지한다.
- `thread_id`는 선택 입력이며, 생략하면 새 대화를 만든다.
- 응답에는 `thread_id`, `evidence_status`, `resolved_question`, `trace_id`, `conflicts`를 추가한다.
- 기존 프론트는 현재 화면 세션의 `thread_id`를 메모리에 유지해 후속 질문에 자동 전달한다. 새로고침이나 프로젝트 전환 시 화면에 보이지 않는 과거 문맥이 섞이지 않도록 새 대화를 시작한다.

## ADR-006: 팀장용 검증 알림을 Railway 이전 로컬 고도화로 배치

- 기록일: 2026-07-30
- 상태: 계획 확정
- 적용 시점: 핵심 검색·판정·UI·데이터 연결·품질·보안 기준 통과 이후, Railway 마이그레이션 이전

### 배경

팀장 합성 소비자 시나리오에서 피비가 질문에 답하는 데 그치지 않고 변경·충돌·미확정 업무를 먼저 알려주는 경험의 가치가 확인됐다. 다만 신뢰할 수 없는 검색·판정 결과를 선제적으로 전달하면 오류의 영향이 커지므로 알림을 현재 1순위로 두지 않는다.

### 결정

- 검색·판정 코어, 웹·모바일 UI, 추가 데이터 연결, 외부 조직 수준의 품질·보안 검증을 알림보다 우선한다.
- 알림은 기존 질문형 검색을 대체하지 않고, 새 데이터와 변경분에서 검증 대상을 찾는 별도 감시 흐름으로 추가한다.
- 1차 접점은 피비 웹·모바일의 `오늘의 검증 브리핑`과 알림함으로 제한한다.
- 알림은 프로젝트별 근거, 판정 이유, 중요도, 발견 시점, 읽음·확인·해결 상태, 중복 방지 식별값을 저장한다.
- 로컬 Docker 중단이나 기기 잠자기 이후 재실행하면 마지막 확인 시점 이후 변경분을 따라잡는다.
- 알림 생성과 로컬 운영 안정성을 검증한 뒤 Railway로 마이그레이션한다.
- 네이버웍스·이메일·모바일 OS 푸시는 Railway 안정화 후 전달 채널로 추가한다.

### 안전 원칙

- 근거가 없거나 판정이 불충분한 경우 사실 알림이 아니라 `확인 필요`로 표시한다.
- 동일 사건과 동일 근거의 알림을 반복 생성하지 않는다.
- LLM의 요약만 저장하지 않고 모든 알림을 원문 근거로 역추적할 수 있게 한다.
- 외부 푸시보다 피비 내부 판정의 정확도, 중복 방지, 사용자 피드백 반영을 먼저 검증한다.

## ADR-007: 문서 검색 위에 업무 상태·시간축 판정 계층 추가

- 기록일: 2026-07-30
- 상태: v0.4.0 알파 구현
- 적용 버전: v0.4.0-alpha.1

### 문제 정의

문서에서 `완료`라는 단어를 찾는 것만으로는 업무 완료를 검증할 수 없다. 수행자가 완료했다고 기록한 뒤 고객이 수정을 요청할 수 있고, Notion의 상태값과 Gmail의 실제 피드백 시점이 다를 수 있다. 문서 수정 시각만 최신성으로 사용하면 과거 사실을 나중에 편집한 문서가 실제 최신 사건처럼 오인될 수도 있다.

### 결정

- 기존 문서·청크·하이브리드 검색은 유지하고, 근거 패킷 이후에 상태·사건·시간축 판정 단계를 추가한다.
- `완료 주장`과 `완료 확인`을 별도 상태로 관리한다.
- 고객·요청자·승인권자의 명시적 승인 또는 완료 확인이 있어야 `완료 확인`으로 판정한다.
- 완료 뒤의 최신 수정·보완·재작업 요청은 업무를 다시 `수정 요청` 상태로 연다.
- 제안, 요청, 승인, 실행, 완료를 서로 다른 사건으로 취급한다.
- Gmail이나 Notion 어느 한 출처를 전역 우선하지 않고, 원문 역할·사건 의미·발생 시점·명시성을 함께 평가한다.
- 시점이 같거나 확인되지 않은 서로 다른 현재 상태는 하나를 선택하지 않고 `충돌`로 보류한다.
- 질문할 때마다 원문에서 상태를 다시 계산하며, 판정 결과는 원문을 대체하는 캐시가 아니라 감사용 스냅샷으로 저장한다.

### 호환성과 범위

- 기존 `POST /api/ask`와 응답 필드는 유지하고 선택 필드 `current_state`를 추가한다.
- 상태 질문이 아닌 일반 사실 질문은 기존 검색·판정 흐름을 그대로 사용한다.
- Calendar·업무관리 서비스·알림·외부 쓰기 기능은 이번 버전에 포함하지 않는다.
- 모든 수집 문서를 사전에 사건·주장 레코드로 변환하는 영구 지식 그래프는 실제 더미 데이터 2차 테스트 이후 필요성을 다시 판단한다.

### 품질 기준

- 완료 후 수정 요청을 완료로 답하는 사례 0건
- 제안·요청·승인·완료 혼동 0건
- 상태 판정의 결정적 근거와 원문 링크 제공률 100%
- 같은 시점의 상충 상태를 임의 확정하는 사례 0건
- 프로젝트 경계를 넘는 상태 근거 혼입 0건

## ADR-008: 판정과 사용자 보고를 분리

- 기록일: 2026-07-30
- 상태: v0.4.0 알파 구현
- 적용 버전: v0.4.0-alpha.2

### 문제 정의

검색과 충돌 판정의 정확도가 높아져도 모든 근거를 한 문단에 나열하면 사용자가 결론을 늦게 이해한다. 특히 담당자와 금액처럼 역할이 다른 값이 함께 검색될 때 원문 사실, 피비의 판정, 다음 행동이 섞여 답변의 명료도가 낮아진다.

### 결정

- 검색·수집·연결 코어와 사용자 보고 계층을 분리한다.
- 판정기는 구조화된 사실과 상태를 만들고, 보고 계층은 이를 `한 줄 결론 → 판정 상태 → 역할별 사실 → 다음 확인` 순서로 표시한다.
- 담당자는 외부 제안 담당자·우리 팀 담당자·최종 승인자를 구분한다.
- 금액은 상대방 제안·우리 측 견적·내부 기록·최종 승인 금액을 구분한다.
- 역할이 다른 값은 충돌로 판정하지 않고, 같은 역할·같은 항목의 값이 다를 때만 충돌로 판정한다.
- 충돌과 근거 부족 판정이 보고 단계에서 임의의 확정 답변으로 바뀌지 않도록 결정적 검증기를 통과시킨다.
- API의 기존 `answer`는 유지하되 구조화 필드 `answer_view`를 추가한다.
- 프런트는 Markdown 문자열 대신 구조화된 DOM으로 답변을 렌더링한다.

### 품질 기준

- 충돌 답변의 첫 문장에서 단일 값을 확정하는 사례 0건
- 담당자 역할이 다른 기록을 충돌로 판정하는 사례 0건
- 제안 금액과 최종 승인 금액을 같은 사실로 표시하는 사례 0건
- 모든 표시 사실의 근거 연결률 100%
- 사용자 화면에 Markdown 제어 문자가 노출되는 사례 0건

## ADR-009: 판정 보고의 사용자 언어와 근거 순서를 고정

- 기록일: 2026-07-30
- 상태: v0.4.0 알파 구현
- 적용 버전: v0.4.0-alpha.3

### 결정

- 내부 판정값 `conflict`는 화면에서 `확인 필요 · 기록 불일치`로 표현한다.
- 답변은 `한 줄 결론 → 세부 내용 → 판단 근거 → 피비의 제안` 순서로 항상 펼쳐서 표시한다.
- 동일 이메일을 반복하는 Gmail 원문·회신은 답변에서 한 개의 핵심 사실로 정리한다.
- 우측 원문 패널에는 핵심 판단 근거를 먼저 배치하고 관련 보조 원문은 추가로 유지한다.
- 데스크톱에서는 대화와 근거 패널 높이를 맞추고 각 패널 내부에서 스크롤한다.

### 품질 기준

- 같은 Gmail 연락처가 핵심 판단 근거에 중복 표시되는 사례 0건
- 답변의 핵심 인용 번호와 우측 원문 근거의 선두 순서 불일치 0건
- 세부 내용과 피비의 제안이 접힌 상태로 숨겨지는 사례 0건

## ADR-010: 검증 상태 기반 적응형 답변과 기간 목록 검색

- 기록일: 2026-07-30
- 상태: v0.4.0 알파 구현
- 적용 버전: v0.4.0-alpha.4

### 문제 정의

ADR-009의 고정 보고 형식은 충돌·상태 질문에는 명확했지만 원인 설명, 목록 조회,
이메일 초안처럼 사용자가 요구한 결과물까지 같은 보고서로 바꾸는 회귀를 만들었다.
또 기간 목록 질문이 일반 유사도 검색으로 처리되어 범위 밖 자료가 선택될 수 있었다.

### 결정

- 질문의 원래 요청은 자유형 답변 본문으로 보존한다.
- `supported`, `conflict`, `insufficient`는 답변 형식이 아니라 확신과 표시 범위를 제어한다.
- 현재 상태 엔진은 현재 상태·단계를 직접 묻는 질문에만 실행한다.
- 기간, 요청 항목, 단일·전체 검색 여부를 검색 계획에 저장한다.
- 기간 목록 검색은 날짜 범위에 맞는 문서만 후보로 만들고 문서별 근거를 수집한다.
- 검색에서 찾지 못한 사실을 데이터에 존재하지 않는 사실로 단정하지 않는다.
- UI는 일반 답변은 자연스러운 본문으로, 충돌·근거 부족·상태는 필요한 구조만 추가해 표시한다.
- 품질 판단과 추가 튜닝은 실제 질문에 대한 사용자 검토를 기준으로 반복한다.

### 호환성과 범위

- 기존 API의 `answer`, `answer_view`, `current_state` 필드는 유지한다.
- `answer_view.body`를 추가하고 기존 사실·상태 구조는 호환 필드로 보존한다.
- 데이터 커넥터, 프로젝트 경계, 동기화 방식은 변경하지 않는다.
